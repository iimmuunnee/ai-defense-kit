거래소와 수탁 서비스의 보안 담당자가 자기 조직의 코드, 지갑 권한, 개발자 컴퓨터를 점검할 때 쓰는 명령줄 도구입니다.

- 저장소의 코드와 git 기록에서 노출된 키, 알려진 취약점이 있는 라이브러리, 지갑·결제·배포 설정의 실수를 찾습니다.
- 지갑과 컨트랙트의 권한, 배포된 웹 페이지의 스크립트, 설정 파일, 실행 중인 컨테이너 이미지가 처음 저장한 기준값과 달라지면 알립니다.
- 하는 일은 읽고 알리는 것뿐입니다. 거래를 보내거나 설정을 바꾸지 않으며, 고치는 것과 대응은 사람이 합니다.

## 명령 넷

| 명령 | 하는 일 | 자세히 |
|---|---|---|
| `adk scan <폴더>` | 코드와 git 기록을 읽어 키, 취약한 라이브러리, 지갑·결제·로그인·GitHub Actions 설정 실수, 받은 코드의 자동 실행 설정을 찾습니다 | [사용법](docs/usage.md) |
| `adk watch init`·`check`·`accept` | 설정한 지갑과 컨트랙트(EVM, XRPL), 웹 페이지의 스크립트, 저장소 파일, 컨테이너 이미지 목록을 기준값과 비교합니다 | [watch.md](docs/watch.md) |
| `adk device` (`init`·`check`·`accept`) | 이 컴퓨터에 파일로 저장된 배포 자격 증명(kubeconfig, Docker, AWS, `gh`)을 찾고, 개발 도구 실행 파일과 자동 실행 지점의 변경을 기준값과 비교합니다 | [device.md](docs/device.md) |
| `adk device wallets` | 이 컴퓨터가 감염되면 가져갈 수 있는 지갑 관련 파일(지갑 확장 프로그램 저장소, 데스크톱 지갑 키 저장 위치, 시드 문구로 보이는 글 파일)의 위치만 보여 줍니다 | [device.md](docs/device.md) |
| `adk assets <도메인>` | 인증서 공개 기록(crt.sh)에서 도메인 아래 이름을 모아 확인할 목록으로 보여 줍니다 | [사용법](docs/usage.md#잊힌-자산-찾기-adk-assets) |

종료 코드는 모든 명령이 [한 표](docs/usage.md#종료-코드)를 따릅니다. `--fail-on`의 기본값은 `high`라 높음 이상 결과가 있으면 1이고, 읽지 못한 대상이 있으면 2입니다(`scan`은 `--strict`일 때만). `adk version`은 버전, 소스 커밋, 내장 데이터의 해시를 보여 줍니다.

## 설치

**릴리스 파일.** GitHub 릴리스에서 운영체제별 실행 파일과 `SHA256SUMS`를 받고, 체크섬과 빌드 출처 증명(`gh attestation verify`)을 확인한 뒤 씁니다. 명령은 [설치와 검증](docs/usage.md#설치와-검증)에 있습니다. 첫 릴리스 `v0.1.0`의 Windows amd64 파일로 체크섬과 빌드 출처 증명을 확인했습니다. macOS와 Linux 파일은 받아서 돌려 보지 않았습니다(확인 필요).

**소스에서 설치.** [Go 1.27.4 이상](https://go.dev/dl/)이 필요합니다. 받을 코드가 바뀌지 않게 태그나 커밋 해시로 고정하세요.

```bash
go install github.com/iimmuunnee/ai-defense-kit/cmd/adk@<태그 또는 커밋 해시>
adk version
```

어느 명령도 관리자 권한이 필요 없습니다. 일반 사용자로 실행하세요.

## 외부 통신과 쓰는 파일

소스 코드에서 확인한 것만 적었습니다. 명령마다 읽는 것, 실행하는 외부 명령, 쓰는 파일은 [읽는 것, 연결하는 곳, 쓰는 파일](docs/what-it-touches.md)에 있습니다.

| 명령 | 연결하는 곳 | 보내는 것 |
|---|---|---|
| `scan` | OSV(`api.osv.dev`), CISA KEV 목록(`raw.githubusercontent.com`) | OSV: 잠금 파일에 적힌 라이브러리의 이름, 버전, 생태계(버전 없이 커밋으로 적힌 의존성은 그 커밋 해시). KEV: 목록을 내려받기만 합니다 |
| `scan --offline` | 없음 | 없음 |
| `watch` | 설정한 RPC 주소, `web-scripts` 페이지의 호스트와 `allowed_hosts`, 웹훅(`ADK_WATCH_WEBHOOK`를 설정한 경우만) | RPC 읽기 요청, 페이지 GET 요청, 웹훅 JSON(대상 key, 결과 번호, 등급) |
| `device` | 없음 | 없음 |
| `assets` | crt.sh | 도메인 이름, adk 버전이 든 User-Agent |

- 코드 내용과 파일 경로는 밖으로 보내지 않습니다. 사용 통계도 보내지 않습니다.
- `watch`는 환경 변수의 프록시를 기본으로 쓰지 않습니다. 외부 연결을 프록시로만 내보내는 망이라면 `--allow-env-proxy`를 주세요. 주지 않으면 네트워크로 읽는 대상(지갑, 웹 페이지)이 모두 "확인 못 함"으로 나옵니다([어디로 연결하나요](docs/watch.md#어디로-연결하나요)).
- 쓰는 파일은 `--out` 폴더의 리포트, `watch`의 기준값과 그 옆의 기록 파일(`adk-watch-*.jsonl`), `device`의 `~/.adk/device-baseline.json`과 그 옆의 기록 파일입니다. 쓸 자리에 링크가 있으면 따라가지 않고 쓰기를 거부합니다.

## 한계 요약

- **찾아서 알리는 도구입니다.** 공격을 멈추게 하지 않습니다. 결과가 없다고 문제가 없다는 뜻이 아니며, 정해진 항목만 봅니다.
- **`scan`은 패턴 기반입니다.** 업무 로직의 허점, 데이터 흐름을 따라가야 보이는 문제, 소스 안에 숨긴 악성 동작은 찾지 못하고 오탐도 있습니다. 탐지율과 오탐률을 잰 벤치마크는 아직 없습니다. [`scan`의 한계](#scan의-한계)
- **`watch`는 기준값이 정상이라고 가정합니다.** 이미 침해된 상태에서 기준값을 만들면 그 상태를 정상으로 봅니다. 점검과 점검 사이에 생겼다가 사라진 변화는 보지 못하고, RPC가 주는 답을 믿습니다. [watch.md의 한계](docs/watch.md#한계)
- **`device`는 정해진 파일만 봅니다.** 운영체제 자격 증명 저장소, 브라우저, 다른 도구의 설정은 보지 않습니다. 관리자 권한을 가진 악성코드는 결과를 속일 수 있고, EDR을 대신하지 않습니다. [device.md의 한계](docs/device.md#한계)
- **`assets`의 결과는 확인할 목록입니다.** 찾은 이름이 내 것인지는 판단하지 않습니다.
- **국내 기준 연결은 참고용입니다.** AI(Claude)가 공식 원문과 대조했고, 전문가 검수는 받지 않았습니다. [국내 기준 연결을 읽는 법](docs/korean-standards.md)
- **증적 파일은 점검 기록입니다.** 해시는 파일이 바뀌었는지 확인하는 용도이며 기준 충족을 증명하지 않습니다. [증적 파일과 SARIF](docs/evidence-and-sarif.md)

## `adk scan`: 코드 점검

### 무엇을 찾나요?

| 이런 일이 생기지 않도록 | adk가 찾는 것 |
|---|---|
| 비밀번호나 키가 새어 나가 남이 내 계정을 씁니다 | 코드와 과거 수정 기록에 남은 비밀번호·키 |
| 지갑 키가 새거나 의도하지 않은 서명에 쓰입니다 | 개인 키·니모닉을 코드나 환경 파일에서 직접 읽는 코드, 요청 본문이나 외부 응답이 서명·전송 함수에 바로 들어가는 코드, EIP-7702 위임 서명(`WL-*`) |
| 배포 경로를 통해 운영 환경의 키를 빼 갑니다 | GitHub Actions의 장기 클라우드 키, 커밋 해시로 고정하지 않은 액션, `write-all` 권한, 풀 리퀘스트 코드를 받는 `pull_request_target`(`CI-*`) |
| 돈을 내지 않았는데 주문이 완료됩니다 | 토스페이먼츠·포트원의 결제 알림을 확인 없이 믿는 코드 |
| 로그인 과정을 속여 계정이 엉뚱하게 연결됩니다 | 카카오·네이버 로그인의 보안 실수 |
| 고객 데이터를 아무나 읽거나 지웁니다 | Supabase(데이터베이스 서비스)의 접근 설정 실수, 브라우저로 나가는 비밀 키 |
| 웹사이트에 넣은 비밀 값을 누구나 꺼내 봅니다 | React 앱의 브라우저로 나가는 환경 변수에 든 비밀 값·토큰 |
| 사용자가 쓴 글이 다른 사람의 브라우저에서 코드로 실행됩니다 | React에서 HTML을 직접 넣는 코드(참고용, 넣는 값은 직접 확인) |
| 외부 서버의 스크립트가 바뀌어 내 페이지에서 실행됩니다 | `integrity` 없이 외부 주소에서 불러오는 `<script src>`(`WEB-001`, 참고) |
| 공격자가 서버에서 명령을 실행하거나 데이터를 빼 갑니다 | PHP에서 사용자 입력이 위험한 함수나 SQL 문에 바로 들어가는 코드, 업로드 파일 이름을 그대로 쓰는 코드 |
| 다른 사이트가 로그인한 사용자의 정보를 읽어 갑니다 | FastAPI(서버 프로그램)의 잘못된 접근 허용 설정 |
| 이미 알려진 구멍으로 공격당합니다 | 내 서비스가 쓰는 부품(라이브러리)의 알려진 취약점. 지금 실제로 공격받는 것(CISA KEV)을 맨 위에 보여 줍니다 |
| 받은 코드를 열었다가 내 컴퓨터가 감염됩니다 | 자동으로 실행되도록 설정된 명령, 악성으로 알려진 부품 |

찾은 문제마다 왜 위험한지, 어떻게 고치는지, 관련된 국내 보안 기준(개인정보 안전성 확보조치 기준, ISMS-P 등)의 어느 조항과 이어지는지를 한국어로 알려 줍니다. 항목별 규칙 번호는 [사용법](docs/usage.md#점검-항목)에 있습니다.

### 실행과 결과

```bash
adk scan ./my-app
```

`./my-app` 자리에 점검할 폴더를 적습니다. 결과는 이렇게 나옵니다.

```markdown
## 지금 당장 고칠 것

1. [치명] 브라우저용 환경 변수에 Supabase 비밀 키 - `.env.local:2`
2. [높음] 코드에 비밀 키가 들어 있음 (generic-api-key) - `app/config.py:3`
3. [높음] CORS가 모든 사이트와 자격 증명(쿠키)을 함께 허용 - `main.py:8`

## 상세

### [치명] 브라우저용 환경 변수에 Supabase 비밀 키

- 번호: SB-002
- 위치: `.env.local:2`
- 판단: 확실
- 근거: `NEXT_PUBLIC_SUPABASE_SERVICE_ROLE_KEY=****`

왜 위험한가요?
... 누구나 웹사이트 코드에서 이 키를 꺼내 데이터베이스 전체를 읽고 쓰고 지울 수 있게 됩니다.

어떻게 고치나요? (세 단계)
1. 환경 변수 이름에서 `NEXT_PUBLIC_`을 뺍니다. ...

**국내 기준**

- 개인정보의 안전성 확보조치 기준 제6조(접근통제) (제6조 제3항): 원문 대조함: Claude (AI), 2026-11-04 · 전문가 검수 전
```

예제 앱(`testdata/e2e/sample-app`)을 인터넷 조회 없이(`--offline`) 점검한 실제 출력을 줄인 것입니다. 키 값은 가려서 보여 줍니다.

```bash
# 파일로 저장 (Markdown, JSON, SARIF, 증적 파일)
adk scan ./my-app --format md,json,sarif --out ../adk-reports/2026-11-05

# CI에서 "높음" 이상 문제가 있으면 종료 코드 1 (--fail-on의 기본값이 high입니다)
adk scan .
```

### 받은 코드는 열기 전에 점검하세요

낯선 사람이 보낸 과제나 코드는 여는 것만으로 내 컴퓨터에서 명령이 실행되도록 꾸며져 있을 수 있습니다. 가짜 채용 과제 유형의 공격을 겨냥한 점검입니다. 보고된 사례([Microsoft 1](https://www.microsoft.com/en-us/security/blog/2026/03/11/contagious-interview-malware-delivered-through-fake-developer-job-interviews/), [Microsoft 2](https://www.microsoft.com/en-us/security/blog/2026/02/24/c2-developer-targeting-campaign/))에서는 저장소를 신뢰하면 VS Code가 저장소의 작업 설정을 실행했다고 합니다. 이 두 글은 요약 도구로만 읽었고 원문 문구는 확인하지 못했습니다.

```bash
adk scan ./받은-과제 --untrusted
```

adk는 코드를 실행하지 않고 파일의 글자만 읽습니다. `AR-*`가 나오면 근거에 적힌 설정을 읽어 보고, 무엇을 하는지 모르면 신뢰하거나 설치하기 전에 멈추세요. 시험해 보려면 명령이 `echo adk-test`뿐인 예제 [`testdata/untrusted/fake-assignment`](testdata/untrusted/fake-assignment)를 점검하세요.

- **`--untrusted`가 따르지 않는 설정:** 저장소가 `.adkignore`, `osv-scanner.toml`, `.gitignore`, `.gitattributes`, 줄 안의 `gitleaks:allow`로 결과를 숨기는 것. 옵션 없이 점검하면 이 설정을 따르며, `.gitignore`, `.gitattributes`, `gitleaks:allow`가 숨긴 것은 알리지 않습니다.
- **`--untrusted`로도 알 수 없는 것:** 잠금 파일이나 기록이 없는 저장소는 대조할 수 없습니다. 링크로 된 잠금 파일, 잠금 파일 없는 `package.json`, 읽지 못한 git 기록은 경고로 알리지만, 얕은 복제나 이력을 고쳐 쓴 저장소는 알아채지 못합니다.
- **근거를 읽는 법:** 설정의 JSON 원문을 해석 없이 보여 줍니다. 가리는 값은 gitleaks가 알아본 값, URL 안의 비밀번호, 이름으로 알 수 있는 환경 변수 값뿐이라 `--password hunter2` 같은 값은 그대로 보입니다. 개인 키처럼 보이는 블록은 안에 명령이 숨을 수 있어 항상 가리고 알리며 등급을 높음 이상으로 올립니다.
- **기존 CI에 주는 영향:** `adk scan`은 `--fail-on` 없이도 높음 이상 결과가 있으면 종료 코드 1입니다([종료 코드](docs/usage.md#종료-코드)). 이전 동작은 `--fail-on none`입니다. 자동 실행 설정이 있는 저장소는 결과가 달라질 수 있습니다. 정상적인 설정은 `.adkignore`에 지문을 적어 무시하세요.

### `scan`의 한계

**"문제없음"이 나와도 문제가 없다는 뜻은 아닙니다.** 받은 코드도 마찬가지입니다. 결과가 없어도 열어도 된다는 뜻이 아닙니다.

- **코드와 공개 기록만 봅니다.** 앱을 실행하거나 서버에 요청을 보내지 않으므로, 실제 동작에서만 드러나는 문제는 찾지 못합니다.
- **PHP 점검은 입력이 같은 줄에 바로 들어가는 경우만 찾습니다.** `$id = ...`처럼 변수에 담아 다른 줄에서 쓰는 코드는 찾지 못합니다.
- **규칙이 패턴 기반입니다.** 업무 로직의 허점이나 규칙에 없는 실수는 찾지 못하고, 오탐도 있습니다. 확신이 낮은 결과는 **"의심"** 으로 표시합니다. 지갑 코드 규칙(`WL-*`)도 줄 모양을 보는 신호이며 데이터 흐름을 따라가지 않습니다([지갑 코드 규칙](docs/usage.md#지갑-코드-규칙-wl-)).
- **코드 속에 숨긴 악성코드는 찾지 못합니다.** 난독화한 코드나 평범한 소스 안의 악성 동작은 보지 않습니다. 자동 실행 설정과 알려진 악성 패키지만 봅니다.
- **스택이 좁습니다.** 맞춤 규칙은 PHP, React, Next.js, FastAPI, Supabase, 일부 지갑 라이브러리, GitHub Actions, 한국 결제·로그인 서비스 일부만 다룹니다. 키와 라이브러리 점검은 다른 언어의 프로젝트에도 쓸 수 있습니다.
- **악성 패키지 점검은 `--offline`에서 DB 내용에 달려 있습니다.** 온라인 조회에서는 `op-vscode@1.0.0`(`MAL-2025-342`)이 나오는 것을 확인했습니다. 오프라인 DB에 `MAL-` 자료가 들어 있는지는 확인하지 못했고, 오프라인 점검은 이를 경고로 알립니다.
- **라이브러리 점검은 버전을 알 때만 합니다.** 잠금 파일이 없거나 링크로 되어 있거나 `>=`처럼 고정하지 않은 라이브러리는 대조하지 못하고 경고로 알립니다.
- **AI 도구 설정은 아는 항목만 봅니다.** `AR-004`에 나오지 않는 것: `command`가 아닌 훅(`http`, `prompt`, `agent`, `mcp_tool`), 설정의 `env` 블록, 프로젝트 스킬과 하위 에이전트의 훅, 플러그인과 마켓플레이스 설정, 저장소 밖의 사용자 설정. 도우미 명령과 `.vscode/mcp.json` 서버가 언제 실행되는지는 일부만 확인했고, 나머지는 설명에 "자동 실행 여부 확인 필요"로 적었습니다.
- **국내 기준 연결은 참고용입니다.** 14개 항목 모두 AI(Claude)가 공식 원문과 대조한 상태이고, **전문가 검수는 받지 않았습니다.** 인증 심사 결과나 법률 자문이 아닙니다.
- **증적 파일은 점검 기록입니다.** 해시는 파일이 바뀌었는지 확인하는 용도이며, 위변조가 없었다는 것이나 기준 충족을 증명하지 않습니다.

점검하지 못한 부분은 숨기지 않습니다. 네트워크 오류 등으로 빠진 점검이 있으면 리포트 맨 위와 터미널에 경고로 알립니다.

## 어떻게 검증했나요?

**확인한 것**

- 규칙의 판정 기준은 업체 공식 자료로 확인한 내용만 씁니다. 확인하지 못한 부분은 규칙 파일에 `확인 필요`로 표시합니다. 근거 기록: [`docs/research/`](docs/research/)
- 규칙마다 걸려야 하는 예와 걸리지 않아야 하는 예로 테스트합니다. 전체 테스트 함수는 500개가 넘습니다.
- 점검하는 저장소의 git 설정이 내 컴퓨터에서 명령을 실행하지 못하는지, 평범한 `git status`에서는 그 명령이 실제로 실행되는 대조군과 함께 테스트합니다.
- SARIF 출력은 OASIS 공식 2.1.0 스키마로 검증합니다.
- 모든 변경을 CI에서 Linux, macOS, Windows로 테스트합니다.

**실제로 돌려 보고 고친 것**

- 실제 OSV 조회에서 `requests@2.31.0`의 같은 취약점이 번호별로 따로 보고되어 6건으로 나왔습니다. 번호와 별칭을 합쳐 3건으로 고쳤습니다.
- 잠금 파일이 깨져 있으면 라이브러리의 오류 문구를 통해 내 PC의 전체 경로가 점검 기록에 들어갔습니다. 가짜 오류로 만든 테스트로는 잡히지 않아서, 실제 라이브러리를 거치는 테스트를 추가했습니다.
- 받은 저장소의 `osv-scanner.toml` 하나로 악성 패키지 결과가 경고 없이 사라지는 것을 실험으로 확인했습니다. `.gitignore`와 `.gitattributes`로도 결과가 사라져, `--untrusted`에서는 이 설정들을 따르지 않게 했습니다.
- 명령 문자열의 키를 패턴으로 가렸더니 악성 명령까지 가려졌습니다. 패턴을 고칠 때마다 다른 입력에서 명령이 다시 가려져서, 패턴을 버리고 설정 원문을 보여 준 뒤 gitleaks가 찾은 값만 가리도록 바꿨습니다.
- 파일 이름에 넣은 줄바꿈과 제어 문자로 리포트 제목을 위조하거나 터미널을 조작할 수 있어, 출력 단계에서 정리하도록 고쳤습니다.

**아직 확인하지 못한 것**

- **탐지 벤치마크가 아직 없습니다.** 심어 둔 구멍을 얼마나 찾는지, 오탐이 얼마나 되는지를 수치로 말할 수 없습니다.
- SARIF를 GitHub 보안 탭에 실제로 올려 보지 않았습니다.
- 받은 저장소 점검은 직접 만든 예제로만 돌려 봤고, 실제 공격 저장소로는 시험하지 못했습니다. 바이낸스 사건의 과제 내용은 알려지지 않았으므로 이 점검이 그런 사례를 찾아낸다고 말할 수 없습니다.
- `watch`는 시험 프로그램 안의 가짜 체인·가짜 웹 서버와 로컬 개발 체인(anvil)으로만 돌렸습니다. 메인넷, 테스트넷, 실제 XRPL 노드에서는 돌려 보지 않았습니다([watch.md의 시험](docs/watch.md#시험)). `device`의 macOS 점검은 CI 러너에서만 돌렸습니다.
- `*.code-workspace`의 작업, Cursor의 MCP 시작 시점, 오프라인 악성 패키지 DB는 확인하지 못해 점검하지 않았거나 경고만 합니다.

## 어려운 말 풀이

| 말 | 뜻 |
|---|---|
| 라이브러리 | 서비스를 만들 때 가져다 쓰는 남이 만든 부품 |
| 잠금 파일 | 어떤 부품의 어떤 버전을 쓰는지 적어 둔 목록 (`package-lock.json` 등) |
| 취약점 | 공격에 쓰일 수 있는 프로그램의 약점 |
| 키, 비밀 키 | 서비스에 접속할 때 비밀번호처럼 쓰는 긴 문자열 |
| git 기록 | 코드를 고쳐 온 과거 기록. 지운 내용도 남아 있을 수 있습니다 |
| 기준값 | 처음 점검할 때 정상이라고 보고 저장해 둔 상태. 다음 점검은 이것과 비교합니다 |
| RPC | 블록체인 노드에 상태를 묻는 주소. 보통 API 키가 들어 있습니다 |
| 웹훅 | 어떤 일이 생겼을 때 다른 서비스로 자동으로 보내는 알림 |
| 오탐 | 문제가 아닌데 문제라고 나온 결과 |
| CI | 코드를 올릴 때마다 자동으로 검사하는 설정 |
