`pull_request_target`로 시작하는 워크플로에서 `actions/checkout`이 풀 리퀘스트 쪽 코드를 내려받도록 `ref`를 정했습니다. 다음 중 하나가 `ref`에 들어 있을 때 알립니다.
- `github.event.pull_request.head`로 시작하는 값(`.sha`, `.ref` 등)
- `github.event.pull_request.merge_commit_sha`
- `github.head_ref`
- `github.event`로 만든 `refs/pull/...` 값

`on`이 문자열, 목록, 맵 어느 모양이든 `pull_request_target`을 찾습니다. 괄호 안 공백(`${{ github.head_ref }}`)과 대소문자는 가리지 않습니다. `ref`를 정하지 않은 체크아웃은 알리지 않습니다.

왜 확인해야 하나요?
`pull_request_target`은 풀 리퀘스트의 기준 브랜치 쪽 설정으로 실행되고, 포크에서 온 풀 리퀘스트에도 `secrets`와 쓰기 권한이 있는 토큰을 쓸 수 있습니다. 보통 `pull_request`는 포크의 풀 리퀘스트에 `secrets`를 주지 않는 점과 다릅니다. 이 권한이 있는 워크플로에서 풀 리퀘스트 작성자의 코드를 내려받아 빌드·테스트·스크립트로 실행하면, 그 코드가 내 `secrets`와 토큰으로 실행됩니다. GitHub Security Lab은 이 모양을 "pwn request"로 설명하며 피하라고 안내합니다.

이 결과는 확신도를 "의심"으로 표시합니다. 이 점검은 내려받은 코드를 뒤 단계에서 실제로 실행하는지는 보지 않습니다. 라벨 확인이나 파일 목록 읽기처럼 코드를 실행하지 않는 용도라면 위험이 낮을 수 있습니다. 그래도 나중에 단계 하나가 추가되면 곧바로 위험해지는 구조입니다.

어떻게 하나요?
1. 코드를 실행할 필요가 없으면 `ref`를 지우세요. 기본값은 기준 브랜치의 코드입니다.
2. 풀 리퀘스트 코드를 빌드하거나 테스트해야 하면 `pull_request` 이벤트를 쓰세요. `secrets` 없이, 읽기 권한 토큰으로 실행됩니다.
3. 풀 리퀘스트 코드를 실행한 뒤 `secrets`나 쓰기 권한이 필요한 일(댓글 달기, 배포)은 `workflow_run`으로 나누는 방법이 있습니다. 이때 앞 워크플로가 만든 산출물도 믿을 수 없는 입력으로 다루세요(세부 수칙은 GitHub Security Lab 글로 확인 필요).
4. 꼭 이 구조를 써야 한다면 작업의 `permissions`를 읽기로 줄이고, 풀 리퀘스트 코드를 내려받는 작업에는 `secrets`를 넣지 마세요.

이 점검의 한계
- `run:` 단계에서 `gh pr checkout`, `git fetch`, `git checkout`으로 풀 리퀘스트 코드를 받는 경우는 보지 않습니다. 이 명령을 쓰는 `pull_request_target` 워크플로는 직접 확인하세요.
- `repository:`로 포크 저장소를 지정한 체크아웃은 `ref`가 없으면 알리지 않습니다.
- `workflow_run` 등 다른 이벤트에서 같은 문제가 생길 수 있는지는 확인하지 않았습니다(확인 필요).
- 환경(Environments)의 승인 규칙과 포크 풀 리퀘스트 실행 승인 설정이 걸려 있는지는 보지 않습니다.
