이 프로젝트의 Next.js 미들웨어(또는 Proxy) 파일이 로그인이나 권한을 확인하는 것으로 보입니다. 이 결과는 "참고"입니다. 취약점이 아니며, 심각도도 낮음입니다.

무엇을 알아야 하나요?
미들웨어에서 로그인을 확인하는 것은 흔하고 괜찮은 방법입니다. 하지만 그것을 유일한 방어선으로 두면 안 됩니다. Next.js 공식 인증 가이드(canary, 미들웨어가 "Proxy"로 불리는 판)는 이렇게 적습니다. "While Proxy can be useful for initial checks, it should not be your only line of defense in protecting your data." (뜻: Proxy는 초기 확인에는 유용하지만, 데이터를 지키는 유일한 방어선이 되어서는 안 된다.) 같은 문단은 보안 검사의 대부분을 데이터 원본에 최대한 가까운 곳에서 하라고 안내합니다.

실제 사례: CVE-2025-29927
Next.js 보안 권고(GHSA-f82v-jwr5-mffw)는 이렇게 말합니다. "It is possible to bypass authorization checks within a Next.js application, if the authorization check occurs in middleware." (뜻: 인가 검사가 미들웨어에서 이루어진다면 Next.js 애플리케이션의 인가 검사를 우회할 수 있다.) 권고 파일의 심각도는 CRITICAL로 표시되어 있습니다. CVSS 점수는 파일에 숫자로 적혀 있지 않아 여기서도 적지 않습니다.
- 영향받는 `next` 버전: 12.0.0~12.3.4(수정 12.3.5), 13.0.0~13.5.8(수정 13.5.9), 14.0.0~14.2.24(수정 14.2.25), 15.0.0~15.2.2(수정 15.2.3).
- 11.x는 영향 범위 목록에는 없고, 권고문은 우회 방법만 안내합니다.
- 우회 방법: 권고문은 `x-middleware-subrequest` 헤더가 들어 있는 외부 요청이 Next.js 앱에 닿지 못하게 막으라고 권고합니다. 리버스 프록시나 방화벽에서 그 헤더를 걸러 내면 됩니다.
- 권고문은 Vercel에 배포한 앱은 이 취약점으로부터 자동으로 보호된다고 적습니다.

이 규칙은 `next` 버전을 보지 않습니다. 잠금 파일(lockfile)이 있으면, 취약한 `next` 버전(CVE-2025-29927 포함)은 의존성 점검이 따로 찾아 알려 줍니다. 버전을 올렸더라도 공식 가이드가 말하듯 미들웨어를 유일한 방어선으로 두지 말고 아래처럼 데이터 가까이에서도 확인하는 것이 좋습니다.

진짜로 해야 할 일
로그인과 권한을 데이터에 가까운 곳에서 다시 확인하세요. 라우트 핸들러, 서버 액션, 데이터 접근 계층(Data Access Layer)에서 세션을 다시 검증합니다. 방법은 fixes 안내를 보세요. 미들웨어의 확인은 빠른 1차 거름망으로만 두면 됩니다.

이 규칙이 보는 것과 놓치는 것
- 루트와 `src/` 아래의 `middleware.ts`, `middleware.js`, `proxy.ts`, `proxy.js` 중 하나에, 인증으로 보이는 글자(`cookies`, `getToken(`, `session`, `auth(`, `/login`, `authorization`)가 있으면 파일당 하나만 알려 줍니다. `session`과 `authorization`은 대소문자를 구분하지 않습니다(`getSession`도 맞습니다).
- 다른 곳(라우트 핸들러, 서버 액션, 데이터 접근 계층)에서 다시 확인하는지는 보지 않습니다. 이미 다시 확인하고 있다면 이 결과는 무시해도 됩니다.
- 인증 라이브러리를 쓰는 형태도 인증 신호로 봅니다: `export { auth as middleware }`, `next-auth/middleware`, `withAuth(`, `clerkMiddleware(`, `.protect(`. 이 형태들을 각 라이브러리의 공식 문서와 대조해 확인하지는 않았고, 코드 모양만 봅니다.
- 글자만 보므로 주석이나 문자열에 `session` 같은 단어가 있어도 맞을 수 있습니다(오탐).
- 알려진 오탐: `request.cookies.get('NEXT_LOCALE')`처럼 쿠키를 읽는 로케일(언어) 미들웨어는 `cookies` 때문에 맞습니다. CORS 헤더 목록에 `Authorization`을 적거나 API 프록시로 그 헤더를 그대로 넘기는 미들웨어도 맞을 수 있습니다.
- 쿠키를 읽지 않고 로케일 리다이렉트만 하는 미들웨어, `NextResponse.next()`만 있는 미들웨어, 보안 헤더(`Content-Security-Policy`, `x-frame-options` 등)만 붙이는 미들웨어는 맞지 않습니다.
- `apps/web/middleware.ts` 같은 하위 경로, `.mjs` 파일은 보지 않습니다.
- 인용한 공식 문서 문장은 canary(Proxy로 이름이 바뀐 판) 기준이며, 이전 이름(Middleware) 문서는 읽지 않았습니다.
