# 사용법

## 점검 항목

| 분류 | 점검 내용 |

| 🧾 외부 스크립트 | `integrity` 없이 외부 주소(`https://`, `//호스트`)에서 불러오는 `<script src>`(`WEB-001`, 참고). HTML과 서버 템플릿 파일만 봅니다. 스택 조건은 없습니다 |
| 🔏 지갑 코드 | `package.json`에 `ethers`, `viem`, `web3`, `@safe-global/*`, `@ethersproject/*`, `hardhat`, `@wagmi/core`가 있으면 적용(`web3`). 이 패키지가 없으면 `WL-*` 규칙은 돌지 않습니다. 개인 키·니모닉을 코드나 환경 파일에서 직접 읽음(`WL-001`), 요청 본문이나 외부 응답이 서명·전송 함수에 바로 들어감(`WL-002`), EIP-7702 위임 서명 사용(`WL-003`, 검토 대상). 아래 [지갑 코드 규칙](#지갑-코드-규칙-wl-)을 보세요 |

| 🚀 GitHub Actions 배포 경로 | `CI-001`~`CI-004`. 아래 [GitHub Actions 점검](#github-actions-점검) 표를 보세요 |
| ☠️ 알려진 악성 패키지 | OSV에 악성 패키지로 올라 있는 라이브러리(`MAL-`)를 치명으로 알립니다. 오프라인 DB에 이 자료가 있는지는 확인하지 못했습니다 |
| 🌐 잊힌 자산 | `adk assets <도메인>`: 인증서 공개 기록에서 서브도메인을 찾습니다. 찾은 주소에 접속하지 않습니다 |
| 👛 지갑 권한 변경 | `adk watch init`, `check`, `accept`: 감시할 EVM 지갑과 컨트랙트를 읽어 처음 저장한 기준값과 달라졌는지 알립니다. 읽기만 합니다. 자세한 내용은 [watch.md](watch.md)를 보세요 |
| 💻 개발자 컴퓨터의 배포 토큰 | `adk device`: 이 컴퓨터의 kubeconfig 고정 토큰(`DV-001`), Docker 저장 인증(`DV-002`), AWS 장기 키(`DV-003`), `gh` 평문 토큰(`DV-004`)을 찾습니다. `adk device init`/`check`는 macOS·Linux에서 개발 도구 실행 파일 바뀜(`DV-101`), Homebrew 밖을 가리키는 링크(`DV-102`), 자동 실행 지점 변경(`DV-103`)도 기준값과 비교합니다. 값은 출력하지 않고 네트워크에 연결하지 않습니다. 자세한 내용은 [device.md](device.md)를 보세요 |
| 🔑 이 컴퓨터에서 가져갈 수 있는 지갑 파일 | `adk device wallets`: 글 파일에 적힌 시드 문구로 보이는 것(`DV-201`), 브라우저의 지갑 확장 프로그램 저장소(`DV-202`), 데스크톱 지갑의 키 저장 위치(`DV-203`), 잠그지 않고 저장하는 키 파일(`DV-204`)의 위치를 목록으로 냅니다. Windows·macOS·Linux에서 됩니다. 낱말, 낱말 수, 값은 출력하지 않습니다. 결과에 없는 것은 찾아본 범위 안에서 없다는 뜻입니다. 자세한 내용은 [device.md](device.md)의 "도난 예상 목록"을 보세요 |

PHP 규칙(`PH-*`)의 한계: 한 줄만 보는 추정이고 구문 분석기가 아닙니다. 결과가 없어도 문제가 없다는 뜻은 아닙니다.
- 공통: 입력을 변수에 담아 다른 줄에서 쓰거나 호출이 여러 줄에 걸치면 찾지 못합니다. 입력 앞에 세 겹 이상 닫힌 괄호가 있어도 놓치고, 문자열 안의 `\"`처럼 따옴표 짝이 어긋나면 결과가 틀릴 수 있습니다. `$_get`처럼 대소문자가 다른 이름은 입력으로 보지 않습니다.
- `PH-001`, `PH-004`: 함수 이름 바로 앞이 `=>`, `case 1:`, `/* 주석 */`이거나 `$a?1:`처럼 공백 없는 삼항이면 놓칩니다. 앞 글자가 `echo`, `print`, `return`, `else`, `or`, `and`, `<?php`가 아닌 단어(`throw`, `yield`, `do` 포함)이거나 한글이면 메서드 정의, 일반 문장, 주석으로 보고 찾지 않습니다. 문장 끝이나 여는 태그 바로 뒤의 `//`, `#` 주석은 빼는데, 문자열 안의 `; #`도 주석으로 봐서 그 뒤의 입력을 놓칩니다. 문장 끝이 아닌 곳의 주석(`foo() // 예전, 함수(...)`), `Press return 함수이름 (" . 입력` 같은 글, 인라인 자바스크립트의 같은 이름 메서드는 잘못 찾을 수 있습니다. `assert`는 찾지 않습니다(PHP 매뉴얼에 따르면 문자열 평가는 PHP 8에서 제거됨, PHP 7 이하 프로젝트는 직접 확인 필요).
- `PH-002`: `=>`, `case 1:`, `if ($a):`, `$a or`, `$a and`, `/* 주석 */` 바로 뒤의 파일 포함은 놓치고, 입력 앞에 `<`가 있어도 놓칩니다. `$pages[입력]` 같은 지도 조회는 찾지 않지만 `$this->pages[입력]`, `$pages[trim(입력)]`은 잘못 찾을 수 있습니다.
- `PH-003`: 따옴표 바로 뒤에 SQL 모양이 오는 글(`"Select a category from the list: "`)은 잘못 찾을 수 있어 "의심"으로 표시합니다. 숫자 변환·이스케이프 호출은 안쪽에 괄호가 없을 때만 빼고, 그 이스케이프가 문맥에 맞는지는 보지 않습니다. 값 분리 호출은 지정한 이름(`->query`, `->prepare`, `execute_query`, `pg_query_params`, `DB::...`)만 빼므로 다른 값 분리 API는 잘못 찾을 수 있고, 값 안의 괄호가 두 겹 이상이어도 그렇습니다. `INSERT IGNORE INTO`, `REPLACE INTO`, `"(SELECT`, SQL 문자열 안의 `;`는 놓칩니다. 문자열 안에 `"floatval(" . 입력`처럼 함수 이름 글자가 있으면 가려서 놓칩니다.
- `PH-005`: `md5(...)`, `sanitize_file_name(...)`는 안쪽에 괄호가 없을 때만 빼므로 `md5(uniqid() . 이름)`은 잘못 찾을 수 있습니다.

## 지갑 코드 규칙 (`WL-*`)

**이 규칙들은 신호입니다.** 줄 모양을 보는 의심 결과이고, 데이터 흐름을 따라가지 않으며 승인 절차나 서명 화면에 보이는 내용이 실제와 같은지도 볼 수 없습니다. 위조된 승인 요청처럼 줄에 드러나지 않는 조작은 이 규칙으로 알 수 없습니다. 결과가 없다고 해서 문제가 없다는 뜻이 아닙니다.

| 번호 | 찾는 것 | 등급 |
|---|---|---|
| `WL-001` | `process.env.<...PRIVATE_KEY>`·`MNEMONIC`·`SEED_PHRASE`, `PRIVATE_KEY=값` 환경 파일 줄, `privateKeyToAccount(`·`new Wallet(`에 환경 변수나 문자열 상수를 바로 넘기는 줄, 키처럼 생긴 상수 | 높음(의심) |
| `WL-002` | `signTransaction`, `signMessage`, `signTypedData`, `sendTransaction`, `writeContract`의 인자 맨 앞이 `req.body`, `ctx.request.body`, `res.data`, `await res.json()`, `await fetch(` 같은 입력인 줄 | 높음(의심) |
| `WL-003` | `signAuthorization`, `authorizationList` 등 EIP-7702 위임 서명. 검토 대상이며 위험이 있다는 뜻이 아닙니다 | 낮음(의심) |
| `WL-004` | 번호만 비워 둡니다. 아래 설명을 보세요 | 규칙 없음 |

- 근거 가림(모든 규칙 공통): `WL-001`의 근거에는 걸린 이름과 `****`만 나옵니다. 다른 규칙의 근거는 다음을 지킵니다(시험으로 확인).
  - 주석은 나오지 않습니다. 파일 종류에 맞는 표시 뒤는 "(주석 생략)"이고, 걸린 줄 전체가 주석이면 "(주석 줄에서 찾음, 내용 생략)"만 나옵니다(환경 파일의 주석 줄은 "(주석 생략)"). 표시는 따옴표와 상관없이 찾으므로 문자열 안의 `//`, `#`도 자릅니다. `https://`처럼 두 글자 이상 주소 형식 뒤의 `//`만 주석으로 보지 않습니다(그래서 `ab://` 모양의 글자도 주소로 봅니다).
  - 이름이 `.env`로 시작하거나 끝나는 파일(`.env` 파일, `.env.local`, `.envrc`, `.env-local`, `.env_local`, `prod.env` 등)은 `=` 뒤의 값을 전부 `****`로 가리고, 이름은 올바른 환경 변수 이름(`export` 가능)일 때만 보입니다. `=`이 없는 줄 같은 그 밖의 줄은 줄 전체를 가립니다.
  - 닫히지 않은 따옴표는 그 뒤를 줄 끝까지 가립니다.
  - 64자리 이상 16진수(어떤 문자로 나눈 묶음이어도 자릿수를 더함)와 단어 11개 이상의 나열은 접두사 없이 가리고 "(64자리 이상 16진수를 가림)" 또는 "(긴 단어 나열을 가림)"이라고 적습니다. 코드 줄이나 명령처럼 쓰인 그대로 보여 주는 글에서 나열로 세는 것은 두 가지입니다. 하나는 공백·쉼표로 나눈 2~8글자 단어(대소문자와 한글 같은 문자 종류는 상관없고 `1.` 같은 번호 가능)이고, 다른 하나는 같은 구분 문자 하나(`/`, `_`, `.`, `-`, `|`, `:`, `;`, `+` 같은 한 글자, 또는 `%20`, `&#160;`, `&nbsp;` 같은 이스케이프 하나)로만 이은 3~8글자 영문 소문자 단어입니다. 그래서 코드 줄 전체로 보면 UPPER_SNAKE 이름, camelCase, 구분 문자가 섞인 모양, 점으로 이은 식별자(`process.env.NEXT_PUBLIC_SUPABASE_URL`)는 나열로 세지 않고 그대로 보입니다. 다만 그 줄 안의 값 하나(문자열 리터럴, 경로, 주소의 호스트·경로·질의 값, 대입의 이름, 16글자 이상 식별자)는 따로 검사하며, 이때는 구분 문자가 섞여도, 대문자여도 단어 11개 이상이면 가립니다. 이 모양은 일반 주소, 해시, 문장일 수도 있으므로 안내 문구가 나왔다고 해서 비밀이 지워졌다는 뜻은 아닙니다.
  - 다른 검사기: 자동 실행 설정(`AR-*`)은 따로 보이는 값(작업 이름, 객체 키, 환경 변수 값, 서버·이벤트 이름)을 하나씩 값 기준으로 검사합니다(구분 문자가 섞여도, 대문자나 한글이어도 단어 11개 이상이면 가림). 명령(`command`, `args`의 항목, `package.json` 스크립트 본문, 도우미 명령)은 전체를 위 코드 줄 기준으로 보고, 공백으로 나눈 낱말마다 값 기준을 더합니다. 그래서 `&&`, `|`로 이은 흔한 명령은 그대로 보이고, `ZOO_QUARTZ_...`처럼 한 낱말로 쓴 구문은 가립니다. 문자열 배열(`args` 등)은 항목을 이어 붙인 모양(공백을 넣어서, 그리고 붙여서)도 코드 줄 기준으로 검사하고, 구분 문자로 끝나는 항목은 다음 항목에, 구분 문자 하나와 2~8글자 단어로만 된 항목(`_QUARTZ`, `--`로 시작하는 것은 제외)은 앞 항목에 바로 붙이고 나머지는 공백으로 이은 모양을 명령 기준으로 한 번 더 검사해(`["ZOO_", "QUARTZ_", ...]`, `["ZOO", "_QUARTZ", ...]`처럼 나눈 구문도 찾음) 그 모양에 든 항목만 가립니다. JSON의 키와 값을 합쳐 세지는 않습니다. CI(`CI-*`)의 작업·서비스 이름과 `uses` 값, Supabase(`SB-001`)의 테이블 이름, `adk assets`의 호스트 이름은 그 이름만 먼저 값 기준으로 검사한 뒤 문장에 넣습니다. 모든 결과는 리포트에 들어가기 전 한 번 더 검사하는데, 도구가 만든 문장 안의 구분 문자를 세지 않도록 이때는 64자리 이상 16진수와 공백·쉼표로 나눈 나열만 봅니다. `adk watch`의 체인 값은 그대로 보여 줍니다. `AR-*`, `CI-*` 근거에 가림 안내가 나오면 파일을 직접 열어 확인하세요.
  - 이 모양에 들지 않는 것은 가린다고 보장하지 않습니다. 10개 이하 단어, 한 글자 단어(중국어 한 글자 단어 포함)나 9글자 이상 단어로 끊긴 나열, 코드 줄에서 구분 문자가 섞이거나 대문자인 나열 중 따로 검사하는 값에 들지 않는 것, 자동 실행 명령이나 인자 하나 안에서 공백과 기호를 함께 끼운 나열(`zoo - quartz | vessel ...`), camelCase(앞 4글자가 보일 수 있음), 16진수가 아닌 글자로 끊긴 키, 63자리 이하 16진수, base58 키, base64 키(앞 4글자가 보일 수 있음), 구분 문자로 보지 않는 이스케이프(`\uXXXX`, `\xXX`, 두 번 인코딩한 `%2520`, `;`가 없는 `&#32`, `&ThinSpace;`나 `&NonBreakingSpace;`처럼 대문자가 섞인 HTML 이름 참조. 8글자를 넘는 공백 이름은 모두 이 경우입니다), 파일 경로(결과 위치)가 그렇습니다. 짧은 내용의 닫힌 문자열과 따옴표 밖 코드는 이전 방식으로 일부만 가려지며 쓰인 그대로 나올 수 있습니다.
  - 지문: 규칙 결과의 지문은 줄 원문이 아니라 리포트에 나오는 가린 근거와 순번에서 만듭니다. 근거는 200글자까지만 나오고 지문도 그 근거에서 만듭니다. 순번은 같은 파일에서 같은 규칙, 같은 가린 근거가 여러 번 나올 때 줄 순서대로 0부터 붙입니다. 가려진 값은 지문 입력에 들어가지 않아, 지문을 다시 계산해 값을 짐작해 맞혀 볼 수 없습니다. 같은 자리의 값이 바뀌어도 지문은 같습니다(한계는 docs/evidence-and-sarif.md). 다른 검사기의 지문은 값이 아닌 구조 정보(설정 항목, `uses` 값, 테이블 이름)에서 만듭니다.
  - 비밀 키 검사(`SECRET-`)는 값 기준 두 모양이 아닌 비밀 값의 앞 4글자를 보여 주고, 지문은 보이는 근거(앞 4글자와 `****`, git 기록은 커밋 포함)와 같은 파일, 같은 규칙, 같은 근거의 순번(줄, 열 순서)으로 만듭니다. 값 자체는 지문에 들어가지 않습니다.
  - 근거가 가려져 있어도 키가 든 파일 자체는 그대로입니다. 저장소에서 지우고 키를 교체하세요.
- `WL-001`은 배포 도구와 시험 코드를 보지 않습니다: 저장소 루트와 `packages/*/`, `apps/*/` 바로 아래의 `scripts/`, `script/`, `deploy/`, `test/`, `tests/` 폴더(그보다 깊은 `src/services/test/`나 `app/api/deploy/`는 봅니다), 어느 깊이든 `__tests__/`, `hardhat.config.*`, `truffle-config.*`, `*.test.*`, `*.spec.*`, `.env.example`, `.env.sample`, `.env.template`, `.env.test`. 이 경로의 파일이 운영 키를 읽는다면 직접 확인하세요.
- `WL-001`은 `new Wallet(key)`처럼 변수를 넘기면 값의 출처를 몰라 찾지 못합니다. `WL-002`도 값을 변수에 담아 다른 줄에서 넘기는 코드와 검증 함수(`parse(req.body)`)를 거친 코드는 찾지 않습니다. 그 함수가 실제로 검증하는지는 보지 않습니다.
- `WEB-001`은 같은 줄에 `integrity`가 있는지만 봅니다. `<script`와 `src=`가 다른 줄에 있는 여러 줄 태그, `<sCrIpT`처럼 대소문자를 섞은 태그, 같은 줄에 `integrity`가 있는 태그와 함께 있는 두 번째 태그는 놓칩니다. `src`는 한 줄에 있고 `integrity`만 다음 줄에 있으면 결과가 잘못 나옵니다. 자바스크립트로 붙이는 스크립트는 보지 못하고, 내용이 정당하게 바뀌는 CDN 스크립트는 SRI가 맞지 않을 수 있습니다.
- 훈련 D7(`testdata/rules/wallet/WL-002/vulnerable/d7`): 외부 응답을 그대로 서명 함수에 넘기는 코드에 `WL-002`가 한 건 나오는지 확인합니다. 코드 모양 신호일 뿐이며, 위조된 승인 요청이나 서명 화면 조작을 알아보는 것은 아닙니다.
- 이 규칙들은 실제 저장소로 오탐과 미탐을 재 보지 않았습니다. 시험 자료(`testdata/rules/wallet`, `testdata/rules/web`)에서만 확인했습니다.

**`WL-004`(서명 서비스를 부르는데 받는 주소·금액 허용 목록이 없는 코드)는 규칙으로 넣지 않았습니다.** 시험 자료로 줄·파일 단위 규칙을 만들어 보았더니 쉽게 만든 예제(취약 3개, 정상 3개)는 구별했지만, 직접 만든 현실적인 모양 7개는 모두 틀렸습니다(실제 저장소가 아니라 직접 쓴 예입니다). 서명 서비스를 부르는 코드에 정해진 모양이 없어 호출을 알아보지 못하거나(함수 이름이 다른 감싸기 함수), 허용 목록이 다른 파일이나 서명 서비스 쪽에 있어도 알 수 없어 오탐이 나왔고(로그인 `sign-in` 주소, 시험용 가짜 호출 포함), 파일에 `limit`(쪽 나누기)나 "allowlist 추가 예정" 주석이 있으면 허용 목록이 있다고 보고 놓쳤습니다. 허용 목록이 실제로 적용되는지는 줄 규칙으로 구별할 수 없다고 판단했습니다. 실제 저장소 측정은 아직 하지 않았고, 번호는 이후를 위해 비워 둡니다.

수정 안내는 파일 언어를 따릅니다. 지갑 코드 규칙은 `web3` 안내, `WEB-001`은 HTML 안내가 나오며 Next.js나 React와 함께 있어도 같습니다.

포트원 규칙(`KR-PAY-002`)의 한계: `api.portone.io/payments`가 있으면 재조회로 보므로 `/cancel` 같은 주소도 넘어갑니다. PHP 파일은 `webhook`이나 `php://input` 글자가 있을 때만 봐서 그 글자가 없는 핸들러는 놓칠 수 있습니다. 다른 언어는 `portone` 글자만 있어도 지적합니다.

수정 안내는 파일 언어를 따릅니다. PHP만 있는 프로젝트의 `.js`, `.jsx` 결과에는 그 프로젝트 스택의 안내인 PHP 안내가 나옵니다.

```bash
# 화면에 Markdown 리포트 출력
adk scan ./my-app

# Markdown, JSON, SARIF 리포트를 파일로 저장
# (adk-report.md, adk-report.json, adk-report.sarif, 그리고 adk-evidence.json)
adk scan ./my-app --format md,json,sarif --out ./report

# SARIF만 화면(표준 출력)에 내기. 증적 파일은 만들어지지 않습니다
adk scan ./my-app --format sarif

# CI에서 "높음" 이상 문제가 있으면 종료 코드 1 (옵션 없이도 같습니다)
adk scan .

# 결과가 있어도 종료 코드 1을 내지 않기
adk scan . --fail-on none
```

| 옵션 | 설명 |
|---|---|
| `--format md,json,sarif` | 리포트 형식. 기본값은 `md`. 두 형식 이상을 함께 쓰려면 `--out`이 필요합니다 |
| `--out <폴더>` | 리포트를 파일로 저장할 폴더. 쓰면 증적 파일(`adk-evidence.json`)도 항상 함께 저장합니다 |
| `--fail-on <등급>` | 이 등급 이상 문제가 있으면 종료 코드 1. 기본값 `high`. `critical`, `high`, `medium`, `low`, `none`(결과와 상관없이 1을 내지 않음) |
| `--strict` | 점검기가 하나라도 실패하면 종료 코드 2 (이 등급 이상 문제가 있으면 1이 먼저) |
| `--offline` | 외부 통신 없이 점검. 의존성 점검은 `--osv-db`가 있을 때만 합니다 |
| `--osv-db <경로>` | 오프라인 모드에서 쓸 OSV 데이터베이스 경로 |
| `--rules-dir <경로>` | 내장 규칙 대신 직접 만든 규칙 폴더 사용 |
| `--untrusted` | 받은 저장소의 설정으로 결과가 숨겨지지 않게 점검. `.adkignore`, `osv-scanner.toml`, `.gitignore`, `.gitattributes`, 줄 안의 `gitleaks:allow`를 따르지 않습니다 |

`--untrusted` 없이 점검하면 저장소의 `.gitignore`가 그대로 적용되어, 거기 적힌 잠금 파일은 의존성 점검에서 빠집니다. 내가 쓰지 않은 저장소는 `--untrusted`로 점검하세요.

## 설치와 검증

릴리스 파일은 GitHub 릴리스 페이지에서 받습니다. 운영체제·CPU별 파일(`adk_linux_amd64`, `adk_darwin_arm64`, `adk_windows_amd64.exe` 등)과 `SHA256SUMS`가 함께 올라갑니다. 릴리스는 `v*` 태그를 푸시할 때 GitHub Actions가 만들며, 첫 릴리스 전에는 이 절의 명령을 실제 파일로 돌려 보지 못했습니다(확인 필요).

```
# 1) 체크섬 확인 (받은 폴더에서)
# Linux
sha256sum -c SHA256SUMS --ignore-missing
# macOS (sha256sum이 없을 수 있음)
grep adk_darwin_arm64 SHA256SUMS | shasum -a 256 -c
# Windows (PowerShell): 출력된 해시를 SHA256SUMS의 해당 줄과 눈으로 비교
Get-FileHash .\adk_windows_amd64.exe -Algorithm SHA256

# 2) 빌드 출처 증명 확인 (GitHub CLI 필요)
gh attestation verify adk_linux_amd64 --repo iimmuunnee/ai-defense-kit

# 3) Linux·macOS는 실행 권한을 주고 버전 확인
chmod +x adk_linux_amd64
./adk_linux_amd64 version
```

- 내려받은 Linux·macOS 파일에는 실행 권한이 없어서 `chmod +x` 없이는 `Permission denied`가 나옵니다. Windows는 `.\adk_windows_amd64.exe version`으로 바로 실행합니다.
- macOS에서 브라우저로 받은 서명 없는 실행 파일은 Gatekeeper가 격리 속성 때문에 실행을 막을 수 있습니다(확인 필요). 흔히 쓰는 해제 방법은 `xattr -d com.apple.quarantine adk_darwin_arm64`이지만, 실제 Mac에서는 확인하지 못했습니다.
- 체크섬은 파일이 올라온 뒤 바뀌지 않았다는 것만 보여 줍니다. 릴리스 페이지가 바뀌면 파일과 `SHA256SUMS`가 함께 바뀔 수 있으므로, 출처 증명 확인이 더 강한 근거입니다.
- 출처 증명은 이 저장소의 릴리스 워크플로가 그 파일을 만들었다는 Sigstore 서명 기록입니다. 코드가 문제없다는 보증은 아닙니다.
- `adk version`은 버전, 소스 커밋, 내장 규칙·설명·고치는 방법·매핑 데이터의 SHA-256 앞 16자를 출력합니다. 같은 소스에서 만든 파일은 운영체제와 상관없이 데이터 해시가 같습니다. 리포트의 "도구 버전"도 같은 값입니다.
- 릴리스 파일은 태그의 버전(`v`를 뺀 값)을 보여 줍니다. 소스 체크아웃에서 `go build`로 만들면 Go가 넣는 의사 버전(예: `0.0.0-<날짜>-<커밋>+dirty`)이 나오고, `go install ...@<태그>`는 모듈 버전이 나옵니다. `dev`는 빌드 정보가 전혀 없을 때만 나옵니다.

## 종료 코드

`scan`, `assets`, `watch`, `device`가 모두 이 표 하나를 따릅니다. `assets`에는 `--fail-on`이 없어 1이 나오지 않습니다. 다른 문서는 이 표를 가리킵니다.

| 코드 | 뜻 |
|---|---|
| `0` | `--fail-on` 이상인 결과가 없고, 읽지 못한 것도 없음 |
| `1` | `--fail-on` 이상인 결과가 하나라도 있음. 읽지 못한 것이 함께 있어도 1이 이김 |
| `2` | 1이 아니고, 읽지 못한 대상이나 점검이 있음. 사용법·설정 오류도 2. 리포트를 쓰지 못하면 `scan`, `device`, `assets`는 결과와 상관없이 2, `watch`만 `--fail-on` 이상 결과가 있으면 1 |

- `--fail-on`의 기본값은 `--fail-on`이 있는 `scan`, `watch`, `device`에서 `high`입니다. `--fail-on none`을 주면 결과가 있어도 1을 내지 않습니다. 이때도 2는 그대로입니다. 정보 등급 결과는 `--fail-on`에 들지 않습니다.
- `scan`은 `--strict`를 줄 때만 실패한 점검을 2로 셉니다. `--strict` 없이 점검 일부가 실패하면 경고만 나오고, 높음 이상 결과가 없으면 0입니다. `watch`와 `device`는 읽지 못한 대상을 항상 2로 셉니다.
- 이전 버전의 `adk scan`은 `--fail-on` 없이 실행하면 결과가 있어도 0이었고, `--strict`에서 실패한 점검이 있으면 결과가 있어도 2였습니다. 지금은 옵션 없이도 높음 이상이면 1이고, 결과가 있으면 1이 먼저입니다. 예전 동작이 필요하면 `--fail-on none`을 붙이세요.

## 받은 저장소 점검 (`--untrusted`)

```bash
adk scan ./받은-과제 --untrusted --format md,json --out ./report
```

`--untrusted`가 하는 일
- `.adkignore`를 읽지 않습니다. `osv-scanner.toml`은 어느 깊이의 것이든 무시하고, 의존성 점검에서 `.gitignore`를 적용하지 않습니다.
- git 기록 점검에서 `.gitattributes`와 줄 안의 `gitleaks:allow`를 따르지 않습니다.
- 증적 파일(`adk-evidence.json`)에 `untrusted: true`를 남깁니다.
- `osv-scanner.toml`을 무시하는 데 쓰는 임시 파일을 만들거나 읽지 못하면 `deps`를 실패로 기록합니다 (`--strict`에서 종료 코드 2).
- git 기록을 읽지 못하면 경고가 나오고 기록 점검 결과가 빠질 수 있습니다. 현재 파일에서 찾은 비밀 키가 함께 사라지지 않도록 점검은 `완료`로 두므로, 종료 코드는 그대로입니다.

옵션 없이도 도는 점검과 한계
- 자동 실행 점검(`AR-*`)은 `--untrusted` 없이도 항상 돕니다. 악성 패키지 점검은 의존성 점검이 돌 때 함께 돌고, `--offline`에 `--osv-db`가 없으면 건너뛰었다고 표시합니다.
- 옵션이 없을 때 숨김 설정을 따르는 동작은 그대로입니다. 알려 주는 것은 `.adkignore`와 `osv-scanner.toml`이 있다는 사실(`AR-006`)과 `.adkignore`가 숨긴 결과 수(경고)뿐이고, `.gitignore`, `.gitattributes`, `gitleaks:allow`가 숨긴 것은 알리지 않습니다.
- 링크로 된 잠금 파일(`package-lock.json`, `npm-shrinkwrap.json`, `yarn.lock`, `pnpm-lock.yaml`, `bun.lock`)과, 의존성을 적었는데 옆이나 점검 폴더 안의 상위 폴더에 잠금 파일이 없는 `package.json`은 대조하지 못하므로 `deps` 경고로 알립니다. 어떤 옵션에서도 같습니다.
- 잠금 파일이나 기록이 없는 저장소는 `--untrusted`로도 대조할 수 없습니다. 얕은 복제나 이력을 고쳐 쓴 저장소는 알아채지 못합니다.
- 자동 실행 점검은 `dist/`, `build/`, `vendor/`, `node_modules`, `.next`, `.venv`, `__pycache__`, `.git` 폴더를 건너뜁니다. 예외가 둘 있습니다. `osv-scanner.toml`은 그 안에서도 찾고(`.git` 제외), `.devcontainer` 바로 아래 폴더는 이름이 그래도 그 안의 `devcontainer.json`을 읽습니다.

| 번호 | 찾는 것 | 등급 |
|---|---|---|
| `AR-001` | `.vscode/tasks.json`에서 `runOn`이 `default`가 아닌 작업(`folderOpen` 등) | 높음 |
| `AR-002` | `devcontainer.json`의 `initializeCommand`(호스트에서 실행) | 높음 |
| `AR-003` | `devcontainer.json`의 `onCreateCommand`, `updateContentCommand`, `postCreateCommand`, `postStartCommand`, `postAttachCommand` | 보통 |
| `AR-004` | `.mcp.json`, `.cursor/mcp.json`, `.vscode/mcp.json`(`servers`, `mcpServers`)에서 `command`, `headersHelper`, `url` 중 하나가 있는 서버. `.claude/settings.json`, `.claude/settings.local.json`의 `hooks` 명령과 도우미 명령(`apiKeyHelper`, `awsAuthRefresh`, `awsCredentialExport`, `fileSuggestion`, `gcpAuthRefresh`, `otelHeadersHelper`, `statusLine`, `subagentStatusLine`) | 보통 |
| `AR-005` | `package.json`의 설치 때 도는 스크립트 | 낮음(참고) |
| `AR-006` | 결과를 바꿀 수 있는 설정 파일 (`.adkignore`, `osv-scanner.toml`) | 낮음(참고) |
| `MAL-*` | OSV에 악성 패키지로 올라 있는 라이브러리 | 치명 |

- 해석하지 못한 파일(깨진 JSON, 1MB 초과, 심볼릭 링크)은 같은 번호로 `의심` 결과를 내고 직접 확인하라고 알립니다. 등급은 그 파일이 낼 수 있는 가장 높은 등급입니다.
- 파일마다 200건까지 알리고, 넘으면 일부만 보여 준다는 `의심` 결과를 하나 더 냅니다.
- 근거는 설정의 JSON 원문입니다. 실행될 명령을 adk가 해석하지 않으며 `dependsOn` 대상은 따라가지 않습니다. `command`, `args`, `script`, `headersHelper`, `url`, OS별 블록을 먼저 보여 주고 나머지 키가 뒤따릅니다. `args`의 항목은 300자에서, 그 밖의 값은 120자에서 `…(잘림)`으로 줄입니다. 가리는 값은 gitleaks가 알아본 값, URL 비밀번호, 이름으로 알 수 있는 환경 변수 값이고 `--password hunter2` 같은 값은 보입니다. 개인 키처럼 보이는 블록은 항상 가리고 알리며 등급이 높음 이상이 됩니다. MCP의 `env`, `headers` 값은 어느 출력에도 넣지 않습니다.
- `MAL-`은 온라인 조회에서 확인했습니다. `--offline`은 오프라인 DB 내용에 달려 있어 경고합니다.
- **`--fail-on` 변경:** 자동 실행 설정이 있는 저장소는 이전과 결과가 달라질 수 있습니다. 정상적인 설정은 아래 `.adkignore`에 지문을 적어 무시하세요. 낮음(참고) 항목은 `--fail-on low`에서만 영향을 줍니다.
- 시험용 예제: `testdata/untrusted/fake-assignment` (명령은 `echo adk-test`뿐). 그 `.adkignore`는 `AR-001`을 숨겨 두어, 옵션 없이는 숨김 경고가, `--untrusted`로는 결과가 나옵니다.

## GitHub Actions 점검

`adk scan`이 스캔 폴더 바로 아래의 `.github/workflows/*.yml`, `*.yaml`을 읽습니다(재사용 워크플로 포함). 파일의 글자만 읽고 아무것도 실행하거나 접속하지 않습니다. 하위 폴더의 `.github`와 `workflows` 아래 폴더는 읽지 않습니다. `--untrusted`와 상관없이 같은 결과가 나옵니다.

| 번호 | 찾는 것 | 등급 |
|---|---|---|
| `CI-001` | 장기 클라우드 키 설정(`container.env`, `services.*.env` 포함): `with`의 `aws-access-key-id`, `aws-secret-access-key`, 워크플로·작업·단계 `env`의 `AWS_ACCESS_KEY_ID`, `AWS_SECRET_ACCESS_KEY`, `google-github-actions/auth`의 `credentials_json`, `azure/login`의 `creds`. `role-to-assume`만 쓰면 알리지 않습니다 | 높음(확신도 확실). 값이 `secrets`를 읽지 않는 식이면 보통(의심) |
| `CI-002` | 커밋 해시(40자리)로 고정하지 않은 `uses`(단계와 작업의 재사용 워크플로). `docker://`은 `@sha256:` 다이제스트가 없을 때. `./` 로컬 액션은 제외 | 보통, `actions/`와 `github/`는 낮음 |
| `CI-003` | `permissions: write-all`(워크플로 또는 작업마다 하나). `permissions`를 워크플로 전체에도 모든 작업에도 지정하지 않은 파일(파일마다 하나) | `write-all`은 높음, 미지정은 정보 |
| `CI-004` | `pull_request_target`로 시작하는 워크플로의 `actions/checkout`이 `ref`로 풀 리퀘스트 쪽 코드(`github.event.pull_request.head`, `github.event.pull_request.merge_commit_sha`, `github.head_ref`, `github.event`로 만든 `refs/pull/`)를 받는 설정 | 치명(확신도 의심) |
| `CI-005` | 워크플로 파일이나 폴더를 읽지 못함(링크, 일반 파일 아님, 1MB 초과), 또는 한 파일의 결과가 200건을 넘어 일부만 보여 줌. 그 파일은 점검을 받지 못했다는 뜻이며, GitHub가 실행하는지는 확인하지 않았습니다 | 보통(확신도 의심) |

- **키 값은 어느 출력에도 넣지 않습니다.** 값이 `${{ secrets.X }}`든 파일에 적은 글자든 근거에는 키 이름, 파일, 줄만 나옵니다. 지문도 값과 무관합니다.
- YAML이 깨진 파일은 파일 이름을 적은 경고로 알리고 나머지 파일은 계속 점검합니다. 링크, 일반 파일이 아닌 것, 1MB 초과는 읽지 않고 경고와 함께 `CI-005` 결과로 남겨 `--fail-on`에 반영됩니다. 링크는 따라가지 않습니다.
- 한계: 값은 읽지 않고 `secrets`를 읽는 식인지만 구분하므로, OIDC로 받은 임시 자격 증명을 `env`에 넘기는 경우는 `CI-001` 보통(의심)으로 알립니다(임시 자격 증명이 맞다고 확인했을 때만 `.adkignore`로 숨기세요). `run:` 단계의 `gh pr checkout`, `git fetch`로 풀 리퀘스트 코드를 받는 경우, 개별 쓰기 권한(`contents: write`), 저장소·조직의 기본 권한 설정과 `secrets` 목록은 보지 않습니다.
- **`--fail-on` 변경:** 워크플로가 있는 저장소는 이전과 결과가 달라질 수 있습니다. `CI-001`(`secrets` 또는 글자 값)과 `write-all`(`CI-003`)은 높음, `CI-004`는 치명, `CI-005`는 보통이라 `--fail-on high`에서 종료 코드 1이 될 수 있습니다. 정상인 설정은 `.adkignore`에 지문을 적어 숨기세요.
- 워크플로가 없는 저장소는 이전과 결과가 같습니다. 점검 상태 목록에 `cicd`가 하나 더 나옵니다.
- 시험용 예제: `testdata/cicd/risky`(걸리는 모양), `testdata/cicd/clean`(걸리지 않는 모양). 값은 모두 자리 표시입니다.

## 잊힌 자산 찾기 (`adk assets`)

내 도메인의 인증서가 공개 기록(인증서 투명성 로그, [crt.sh](https://crt.sh))에 남긴 서브도메인을 모아 보여 줍니다. 잊고 있던 테스트 서버나 옛 서비스를 찾는 데 쓰세요.

```bash
# 도메인 이름으로 조회
adk assets example.com

# 이미 아는 이름을 빼고, 모르는 것만 보기
adk assets example.com --known known.txt
```

- 결과는 취약점이 아니라 **확인해 볼 목록**입니다. 인증서 기록만으로는 그 이름이 내 것인지 알 수 없어 모두 **"소유 미확인"** 으로 표시합니다.
- 공개 기록만 조회합니다. **찾은 주소에 접속하지 않고**, 이름으로 DNS 조회도 하지 않습니다.
- `adk assets`에는 `--fail-on`이 없습니다. 찾은 이름은 문제 결과가 아니라 목록이라 종료 코드 1을 만들지 않고, "지금 당장 고칠 것"에도 들어가지 않습니다. 조회에 실패하면 "찾은 것이 없음"으로 보이지 않고 점검 실패로 알리며, 종료 코드는 2입니다. 위 표에서 1이 없는 경우입니다.
- 인터넷 조회가 필요해서 `--offline`은 쓸 수 없습니다.

`known.txt`는 아는 이름을 한 줄에 하나씩 적습니다. `#` 주석과 빈 줄은 무시하고, 대소문자는 가리지 않습니다.

```text
# 운영 중인 것
example.com
www.example.com
api.example.com   # 결제 API

# 아래 이름은 모두 아는 것으로 봅니다 (sub.example.com 자신은 해당하지 않음.
# 다만 *.sub.example.com 와일드카드 인증서로만 본 sub.example.com은 아는 것으로 봅니다)
*.sub.example.com
```

| 옵션 | 설명 |
|---|---|
| `--known <파일>` | 아는 이름 목록. 여기에 없는 이름만 "모르는 이름"으로 구분해 보여 줍니다 |
| `--exclude-expired` | 이미 만료된 인증서는 조회에서 뺍니다 |
| `--format`, `--out` | `adk scan`과 같습니다. 다만 `sarif`는 쓸 수 없습니다 (종료 코드 2, 네트워크 조회 전에 거절합니다). `--out`을 쓰면 증적 파일도 저장합니다 |
| `--strict` | 점검이 하나뿐이라 실패하면 항상 종료 코드 2입니다 (켜지 않아도 같습니다) |

`adk assets`의 종료 코드는 위 [종료 코드](#종료-코드) 표를 따릅니다. 이 명령은 점검이 하나뿐이라 점검이 실패하면 `--strict` 없이도 2입니다.

## 🙈 결과 무시하기

오탐이거나 알고도 두는 문제는 점검 폴더의 `.adkignore`에 리포트에 나온 **지문**을 한 줄에 하나씩 적으세요.

```text
# 테스트용 가짜 키라서 무시
69a4bc9105e945d9
```

무시한 개수는 리포트 요약에 `무시함: N개`로 남습니다. 무시한 사실도 숨기지 않습니다.

**지문이 바뀐 결과(이번 판):** 규칙 결과와 비밀 키 검사(`SECRET-`)의 지문은 이제 원문 줄이나 값의 앞 4글자 대신 보이는 근거와 순번으로 만듭니다. 이런 결과를 전에 `.adkignore`로 숨겼다면 새 리포트의 지문을 `.adkignore`에 다시 적어야 합니다. 줄이 움직이면 바뀌던 이전 지문과 달리, 새 지문은 줄이 움직여도 바뀌지 않습니다.
