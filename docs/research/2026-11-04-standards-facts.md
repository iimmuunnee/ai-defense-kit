# 국내 기준 원문 대조 결과

조사일: 2026-11-04. 대조한 사람: Claude (AI). 법적 해석이 아니라 "원문에 그 내용이 있는지"를 확인한 기록이다 (설계 문서 7.7절).
대상 원문은 세 가지다. 안전성 확보조치 기준, ISMS-P 인증기준(별표 7), KISA 주통기 상세가이드의 Web Application(웹) 장.
항목 파일은 `mappings/pipc-safe/`, `mappings/isms-p/`, `mappings/ciip-web/`에 있고, 결과 종류와의 연결은 `mappings/kinds.yaml`과 각 규칙의 `mappings:`에 있다.

## 1. 원문을 받은 방법

### 1-1. 받은 곳과 날짜 (확인됨, 2026-11-04)
- 원문 세 가지는 컨트롤러가 2026-11-04에 공식 사이트에서 직접 받았다. 이 작업에서는 그 사본을 읽었다.
- 국가법령정보센터(`www.law.go.kr`)는 이 환경에서 바로 열렸다. 이 작업 중에도 두 고시의 쪽 주소와 안전성 확보조치 기준 본문을 다시 받아 대조했다(2-3절, 3-2절).
- KISA(`www.kisa.or.kr`)는 TLS 인증서 검증이 실패했다. 1-2절 참고.

### 1-2. KISA 인증서 체인 (확인됨, 2026-11-04)
- `www.kisa.or.kr` 서버는 서버 인증서만 보내고 중간 인증서를 보내지 않았다.
  - 서버 인증서: `CN = *.kisa.or.kr`, `O = Korea Internet and Security Agency`, 발급자 `CN = GeoTrust TLS RSA CA G1` (DigiCert Inc), 유효기간 2026-08-27 ~ 2027-03-13.
  - 그래서 시스템 루트만으로는 체인을 만들 수 없어 검증이 실패했다.
- 컨트롤러가 빠진 중간 인증서(GeoTrust TLS RSA CA G1)를 crt.sh에서 받아, 시스템 루트 인증서에 이어지는지 검증했다. 그 묶음(`kisa-ca.pem`)을 `curl --cacert`로 넘겨 받았다.
- TLS 검증은 끄지 않았다. 중간 인증서만 보충했고, 루트는 시스템에 있는 것을 그대로 썼다.

### 1-3. 받은 파일 (확인됨)
| 원문 | 받은 형태 | 확인 값 |
|---|---|---|
| 안전성 확보조치 기준 | 본문 HTML을 텍스트로 바꾼 것 | 3-2절의 문장 4개를 실제 본문 HTML에서 다시 찾음 |
| ISMS-P 별표 7 | 원본 PDF 9쪽 + `pdftotext -layout` 텍스트 | PDF SHA-256 `1697127f30a92fe3a1b022dd04072c4c201b38391633f1d9deefcfb3810c3512` |
| 주통기 상세가이드 | 원본 PDF 873쪽 중 676~786쪽 텍스트 | PDF SHA-256 `44fe393981b244147be6af7423d99dc15633c089fad0bcb296cbe2371dde812d`, 생성일 2025-12-23 (Hwp 2020) |

- ISMS-P 표는 텍스트로 바꾸면 칸이 섞여 이름이 잘린다. 그래서 항목 이름과 상세 내용은 PDF 9쪽을 화면으로 직접 읽어 확인했다.
- 모든 항목의 `quote`는 텍스트 사본에서 공백을 빼고 글자 그대로 들어 있는지 기계로 다시 확인했다. 모두 들어 있다. 표 칸 이름이 사이에 끼는 3개(ISMSP-1.2.1, ISMSP-2.5.5, CIIP-WEB-IL)는 칸 이름을 빼고 확인했다.
- 가운뎃점은 원문대로 `ㆍ`(U+318D)를 썼다. 주통기 가이드 제목의 `·`도 원문대로다.

- 「2026 주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드」(KISA, 873쪽, 게시 2025-12-24)
- 게시물: https://www.kisa.or.kr/2060204/form?postSeq=22

- Chapter 10 "Web Application(웹)"만 썼다 (PDF 676~786쪽). III장 "웹 서비스"(WEB-01~26)는 웹 서버 설정 항목이라 쓰지 않았다 (컨트롤러 결정).
- PDF 쪽 번호와 인쇄된 쪽 번호가 같다 (708·715·733쪽에서 확인).
- `source_version`: `KISA 2026 주요정보통신기반시설 기술적 취약점 분석·평가 방법 상세가이드 (2025-12-24 게시)`

### 4-2. 사용한 항목 (확인됨)
| ID | 항목 머리의 번호·이름 | 쪽 | 점검 내용 (원문) |
|---|---|---|---|
| CIIP-WEB-IL | IL (상) 5. 정보 누출 | 708 | "웹 애플리케이션 내 중요 정보(개인정보, 금융 정보 등) 및 불필요한 정보(주석 내 디버깅 정보, 초기 샘플페이지, 백업 파일 등)의 노출 여부 점검" |
| CIIP-WEB-CF | CF (상) 7. 크로스사이트 요청 위조(CSRF) | 715 | "웹 애플리케이션 내 사용자의 인증 세션을 악용하여 의도하지 않은 위조 요청 가능 여부 점검" |
| CIIP-WEB-IN | IN (상) 11. 불충분한 권한 검증 | 733 | "타 사용자의 권한을 탈취하여 민감한 데이터 접근 및 수정 가능 여부 점검" |

- 연결 근거로 쓴 다른 칸 (확인됨):
  - CF 조치 방법: "중요한 요청에는 CSRF 방어 토큰을 포함하고, 서버 측에서 해당 토큰의 유효성을 검증하도록 설정하며, Referer/Origin 헤더 검증 및 SameSite 쿠키 옵션을 활용하여 불필요한 외부 도메인 요청이 차단되도록 구성"
  - IN 조치 방법: "접근 제어가 필요한 모든 페이지에 서버 사이드 방식 사용자 권한 검증 로직 구현"
  - IL 판단 기준: "취약 : 중요 정보가 평문으로 노출되거나, 서비스 운영 및 서버 사이드의 구조를 파악할 수 있는 과도한 정보가 노출되는 경우"
- 웹 장 안에서 "OAuth", "CORS", "Access-Control", "웹훅"은 나오지 않는다. "state"는 코드 예시의 다른 낱말(`PreparedStatement`, `IllegalStateException`, `sessionState`)에서만 나온다 (텍스트 검색, 2026-11-04). 그래서 KR-AUTH·FA-001의 CF 연결은 CSRF 일반 요구에 기댄 것이다.

### 4-3. 원문의 표기 차이 (참고, 확인됨)
- 목차는 "6. 크로스사이트 스크립팅", 항목 표와 항목 머리는 "크로스사이트 스크립트"다.
- 항목 표는 "관리자 페이지 노출", 항목 머리는 "19. 관리자페이지 노출"이다.
- 항목 표는 "자동화 공격"의 코드를 AU로 적지만, 항목 머리(777쪽 부근)는 CC로 적혀 있다. 이번에 쓴 항목은 아니다.
- 이름은 항목 머리 표기를 따랐다.

결과: 항목 14개(안전성 확보조치 기준 3, ISMS-P 8, 주통기 웹 3), 모두 `checked`. 설계 문서 7.7절의 목표(15~20개)보다 하나 적다. 원문이 직접 뒷받침하지 않는 항목을 채워 넣는 것보다 보수적인 연결이 낫다고 보아 그대로 두었다 (리뷰 수정, 2026-11-04).

## 7. 남은 것 (확인 필요)
- 전문가 검수(`expert`)는 아직 없다. 리포트는 "AI가 원문과 대조함, 전문가 검수 전"으로 표시된다.
- 연결은 "결과가 보여 주는 것과 원문 요구가 직접 맞는가"로만 판단했다. 어느 사업자에게 그 고시가 법적으로 적용되는지(개인정보처리자인지, 인증 대상인지, 주요정보통신기반시설인지)는 판단하지 않았다.
- 몇몇 연결은 조건이 붙는다. 암호키일 때(ISMSP-2.7.2), 테이블에 개인정보가 있을 때(PIPC-SAFE-6-3).
- ISMS-P 고시와 안전성 확보조치 기준이 이후 개정되면 `source_version`과 `quote`를 다시 대조해야 한다.
- RFC 6749 10.12절 원문은 열지 못했다 (KR-AUTH 규칙 주석과 같음).
