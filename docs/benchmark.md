# 벤치마크 (최소판)

adk가 무엇을 찾고 무엇을 놓치는지를, 누구나 같은 결과를 다시 얻을 수 있는 시험으로 잽니다. 숫자는 퍼센트가 아니라 건수로 적습니다. 표본이 작아서 비율로 말하면 과장이 됩니다.

- 두 시험 모두 `go test ./...`에 들어 있어 CI가 모든 변경에서 돌립니다.
- 결과는 저장소에 둔 기준 파일과 비교합니다. 한 칸이라도 바뀌면 시험이 실패합니다. 규칙이나 필터를 고쳐 진짜 결과를 지우면 바로 드러나게 하려는 것입니다.
- 의도한 개선이면 `ADK_BENCH_UPDATE=1`로 기준을 갱신하고, 바뀐 기준 파일을 함께 커밋합니다. `ADK_BENCH_MD=<파일>`을 주면 아래 표를 다시 만들 수 있습니다.

## 1. 비밀 키 놓침 표

키 종류 6가지 × 놓인 자리 13가지에 가짜 키를 하나씩 심고, 비밀 키 점검이 찾는지 봅니다. 키는 시험을 돌릴 때 고정된 씨앗의 난수로 만들고 저장소에는 두지 않습니다. 씨앗을 고정한 이유는 아래 "문자열 이어붙이기"처럼 값에 따라 결과가 갈리는 칸이 실행마다 흔들리지 않게 하려는 것입니다.

- 시험: [`internal/checker/secrets/recall_test.go`](../internal/checker/secrets/recall_test.go)
- 기준: [`testdata/bench/secrets-recall.json`](../testdata/bench/secrets-recall.json)

```bash
ADK_BENCH_MD=recall.md go test -run TestSecretsRecallTable ./internal/checker/secrets/
```

읽는 법:

- **의심**은 찾았지만 시험·예제 폴더나 문서라서 확신을 낮춘 결과입니다. 등급과 종료 코드는 그대로입니다.
- **건너뛰는 폴더**는 설계상 보지 않습니다(`node_modules`, `vendor`, `.venv`, `dist` 등).
- **문자열 이어붙이기**는 키를 가운데에서 둘로 나눠 `"앞" + "뒤"`로 적은 경우입니다. Slack, Stripe, 개인 키는 앞 절반만으로도 각 형식 규칙에 맞아 찾습니다. GitHub 토큰과 일반 키는 앞 절반이 일반 규칙(`generic-api-key`)의 무작위성 기준을 넘어서 찾은 것이라, 값에 따라 놓칠 수 있습니다(시험 중 다른 값으로 한 번 놓친 것을 보았습니다). AWS 키는 앞 절반이 어느 규칙에도 맞지 않아 놓칩니다.
- **base64로 감싼** 키는 모두 놓칩니다. 인코딩을 풀어 보지 않기 때문입니다.
- **이름 없는 JSON 값**에서 형식이 정해진 키(접두사가 있는 키)는 찾지만, 이름이 없는 무작위 값은 찾지 못합니다.
- **1MB 넘는 파일**은 현재 파일 점검에서는 건너뛰지만, 이 표에서는 커밋된 파일이라 과거 기록 점검이 찾았습니다. 커밋하지 않은 1MB 넘는 파일은 찾지 못합니다. 과거 기록도 한 번의 변경이 5MB를 넘으면 건너뛰고 경고로 알리므로, 5MB 넘게 한 번에 커밋된 파일 속 키는 찾지 못합니다([점검 시간 제한](usage.md#점검-시간-제한과-걸린-시간)).

## 2. 정답표가 있는 예제 앱

예제 앱을 실제 점검 순서(`adk scan --offline`)대로 돌리고, 정답표와 비교해 찾은 것, 놓친 것, 정답표 밖 결과(오탐 후보)를 셉니다. 의존성 결과는 시험용 가짜 자료에서 나오므로 세지 않습니다.

- 시험: [`internal/cli/bench_test.go`](../internal/cli/bench_test.go)
- 정답표: [`testdata/bench/answers/`](../testdata/bench/answers/)
- 기준: [`testdata/bench/cases-result.json`](../testdata/bench/cases-result.json)

```bash
ADK_BENCH_MD=cases.md go test -run TestBenchCases ./internal/cli/
```

| 예제 | 무엇 | 정답 | 찾음 | 놓침 | 정답표 밖 결과 |
|---|---|---|---|---|---|
| [sample-app](../testdata/e2e/sample-app) | 결제·로그인·Supabase·FastAPI 문제를 넣은 앱 | 10 | 10 | 0 | 0 |
| [fake-assignment](../testdata/untrusted/fake-assignment) | 자동 실행 설정을 넣은 가짜 채용 과제 (`--untrusted`) | 6 | 6 | 0 | 0 |
| [clean-app](../testdata/bench/cases/clean-app) | sample-app과 같은 기능을 문제 없이 짠 앱 | 0 | 0 | 0 | 0 |
| [tricky-app](../testdata/bench/cases/tricky-app) | 패턴 규칙이 놓치기 쉬운 모양으로 넣은 문제 | 4 | 2 | 2 | 0 |

tricky-app에서 놓친 것:

- `FA-001` `main.py`: 허용 출처를 환경 변수에서 읽고 기본값이 `"*"`인 경우. 규칙은 코드에 `"*"`가 직접 적힌 경우만 봅니다.
- `KR-AUTH-001` `app/login/route.ts`: `state`를 만들어 쿠키에는 넣었지만 인가 요청 주소에는 빠뜨린 경우. 규칙은 파일에 `state` 값이 있는지만 봅니다.

처음에는 `PH-003` `public/order.php`(입력을 변수에 담아 다른 줄에서 SQL 문에 붙인 경우)도 놓쳤습니다. 2026-11-18에 같은 함수 안의 변수를 따라가게 고친 뒤로는 찾습니다. 이 예제를 알고 고친 것이라, 다른 코드에서도 같은 비율로 찾는다는 뜻은 아닙니다.

## 이 숫자로 말할 수 없는 것

- **예제는 규칙을 만든 사람이 썼습니다.** sample-app과 fake-assignment는 규칙을 만들면서 함께 만든 것이라 모두 찾는 것이 당연합니다. 이 두 줄은 탐지 능력이 아니라 "고치다가 깨뜨리지 않았는가"를 봅니다.
- **tricky-app의 정답표는 adk를 돌리기 전에 적었습니다.** 그래도 문제를 고른 사람이 한계를 알고 고른 것이라, 실제 코드에서 놓치는 비율을 뜻하지 않습니다.
- **clean-app 0건이 "오탐이 없다"는 뜻은 아닙니다.** 실제 저장소에서는 시험 파일, 문서, 해시 값 등에서 오탐이 나옵니다. 실제 공개 저장소로 잰 오탐 수치는 아직 공개하지 않았습니다.
- **판정한 사람이 한 명입니다.**
